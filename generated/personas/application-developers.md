# Application Developers (Resource Consumers)

> Your application can use services that run in other environments. Skupper provides local connection endpoints for those services — whether your application runs on Kubernetes or a Linux host — so you can develop and deploy while dependencies remain managed by other teams.

For this audience, Skupper turns a remote service relationship into a local connection endpoint. The application still owns its protocol behavior, authentication, timeouts, retries, and response to connection loss.

On Kubernetes, this persona aligns with the OpenShift **Resource Consumer** role — the developer working within a scoped namespace who consumes shared platform resources. On Linux hosts, the equivalent is a developer or process owner whose application connects to locally exposed TCP endpoints provisioned by a site owner.

## Access boundary

Application developers consume services without needing access to site or link configuration. What that means depends on the environment:

### On Kubernetes

- Operate with `edit` or `view` roles within their namespace
- **Use** listeners that expose remote services as local Kubernetes Services
- **Deploy** workloads that connect to Skupper-provisioned services
- **Monitor** application topology and connection health via the developer console
- **Consume** Secrets and ConfigMaps generated by Skupper for service discovery

### On Linux hosts

- **Connect** to local TCP endpoints exposed by Skupper listeners on the host
- **Configure** application connection strings to use the listener's host and port
- **Monitor** connection health through application-level checks or Skupper CLI status

In both cases, developers do **not** typically need permissions to create sites, establish links, manage access grants, or modify connectors — those responsibilities belong to Resource Owners (Platform Engineers).
